# AST construction vs AST evaluation: the compiler needs construction only

*2026-07-03*

**What happened.** After adding `quote`, `quasiquote`, and `unquote` to the spec, I realized the requirements conflated two distinct mechanisms: (1) **AST construction** — building AST values programmatically via `quote`/quasiquote, and (2) **AST evaluation** — executing an AST value as code at runtime (`eval` or top-level `unquote`). The compiler needs #1 to construct instructions: `` `(i64.const ,n)`` where `,n` evaluates the expression `n` to embed its value. But the compiler does NOT need #2 — taking an arbitrary AST value and executing it dynamically. That's meta-interpretation: running code whose structure isn't known until runtime, incredibly difficult to implement in a static language because you'd need an interpreter embedded in every compiled program.

**Why.** Inside quasiquote, `,expr` (unquote) just means "evaluate `expr` normally and use its value here" — that's ordinary evaluation producing a value to embed in the AST being constructed. This is statically checkable: the compiler knows `expr`'s type at compile time. But top-level `(unquote ast-value)` or `(eval ast-value)` means "execute this AST as code" — meta-interpretation where the AST's structure is data, not known statically. The seed interpreter can provide `eval` (it's already an interpreter), but a static generation doesn't need it. The compiler **constructs** AST (instructions to emit), **analyzes** AST (the input program), but never **executes** AST that wasn't statically known. Macros might use `eval` at compile-time, and a REPL uses it for interactive evaluation, but the core compiler doesn't. Conflating construction and evaluation makes `eval` look core when it's actually an optional metaprogramming affordance.

**The requirement it drove.**

`spec/capabilities/metaprogramming.md` §"Quote And Quasiquote Construct AST Values": The expression `(quote <expr>)` MUST produce an AST sum type value representing `<expr>`'s structure without evaluating `<expr>`. The expression `` `<template>`` (quasiquote) MUST produce an AST value with selective evaluation: `,<expr>` evaluates `<expr>` and embeds its result in the constructed AST. These are **construction** primitives — they build AST data. The compiler MUST use quasiquote to construct instruction AST values.

`spec/capabilities/metaprogramming.md` §"Eval Is Optional For Macros And Interactive Use": The expression `(eval <ast-value>)` evaluating an AST value as code is an **optional** metaprogramming affordance, not a core compiler requirement. A generation that realizes macros or a REPL MAY provide `eval` to execute compile-time or interactive code. A generation that does not realize macros or interactive evaluation need not provide `eval`. The compiler MUST NOT require `eval` to compile programs — it constructs and analyzes AST but does not execute dynamically-constructed AST.

Removed: the earlier requirement that `(unquote <ast>)` as a top-level form evaluates AST as code. Top-level `unquote` is syntax sugar for `eval` and shares its optional status. Inside quasiquote, `,` (unquote) is a construction operator, not an evaluation operator.
