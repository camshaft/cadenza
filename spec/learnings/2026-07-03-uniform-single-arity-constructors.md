# Uniform single-arity constructors eliminate cascading special cases

*2026-07-03*

**What happened.** While implementing pattern matching for sum types in the seed interpreter, I represented nullary variants (like `None`, `Sign.Zero`) as pre-constructed Sum values in the prelude, while unary+ variants (like `Some`) were Constructor values that produce Sums when applied. This dual representation forced the pattern matcher to have separate branches: one for bare names that might resolve to nullary Sums (evaluate the name, check if it's a Sum, match structurally), and another for constructor patterns `(Ctor arg)` (evaluate the head, check if it's a Constructor, recurse on the binder). The prelude-building code had special cases (some variants bound as Sums, others as Constructors). When I attempted to add unit return support to the compiler, I discovered the brittleness: every consumer (pattern matcher, type synthesizer, emitter, wasm encoder) needed "is this the special kind?" checks. Adding unit required checks in 5+ places (synth-kind, valtype encoding, core-prefix, multi-def-types, envelope-tail, emit-expr). One missed check broke all tests — the differential gate went from 6 witnesses passing to 0 agree, 19 disagree.

**Why.** The design violated the uniformity principle by treating one mechanism (sum type construction) as two mechanisms based on arity. Nullary variants were "pre-applied" (the prelude contained the final Sum value), while unary+ variants were "constructors" (the prelude contained a function that produces the Sum when applied). This arity-based split forced every downstream consumer to replicate the distinction: "is this a nullary Sum or a Constructor?" Pattern matching needed two code paths. Type synthesis needed to know which kind each variant was. The compiler emitter needed special encoding for unit (zero results) vs other types (one result). Special cases compound: each new feature (unit support, more value forms, multi-arity constructors) must check "which special kind is this?" in every place that touches constructors. The brittleness surfaced when adding unit broke unrelated tests — the special-case web was too tangled to extend safely.

**The requirement it drove.** `spec/capabilities/core-semantics.md` §"A Sum Type Constructor Is A Single-Arity Function Producing The Tagged Variant": A sum type constructor MUST be represented as a single-arity function that, when applied to exactly one argument, produces a Sum value tagged with the constructor's variant name. A "nullary" variant is a Constructor whose argument type is Unit, not a pre-constructed Sum value. Construction is always via application: `(Some 5)`, `(None unit)`, `(Sign.Zero unit)` — uniform syntax. Patterns are always `(Ctor binder)`: `(Some x)`, `(None _)`, `(Sign.Zero _)` — uniform structure. The prelude MUST bind Constructor values only, never pre-applied Sum values. The pattern matcher MUST have one branch for constructor patterns `(Ctor binder)`, not separate paths for "bare name that might be a nullary Sum" vs "constructor application". The reader (syntax sugar layer) MAY desugar bare `None` → `(None unit)` in expression position and bare `None` → `(None _)` in pattern position, but the interpreter and compiler core MUST see only the uniform single-arity application form.
